ExplainWhy

An agent that explains why your data sources disagree, and answers only with claims a critic has checked against the query results.

NVIDIA NemotronZetaris data harnessMeterless World Model · H-MEM · Markovian
Team gheware (solo) · Rajesh Ghewaregithub.com/brainupgrade-in/explainwhy
The problem

"Why don't these numbers line up?" costs analysts hours

  • A revenue series that just stops in 2018.
  • A join that silently drops one company.
  • Two figures for the same thing that don't match.

The cause is spread across sources: tagging changes, reference-data gaps, duplicated filings, real business events.

A plain LLM is the wrong tool

It answers fluently, invents numbers, and mixes plausible causes with facts. You cannot tell which sentence came from the data.

ExplainWhy works like a careful analyst: hypotheses → checks → ruled out → only what the data shows, with receipts.

What it does

Hypotheses, SQL evidence, a strict critic, a verified answer

RecallH-MEM brings back prior verified findings, to re-check before use
→
Plan3–5 competing hypotheses: data artifacts and real-world causes
→
Investigateone bounded step at a time: read-only SQL in Zetaris, every result recorded as evidence E-xxxxxx
→
Critiquecitations exist · numbers appear in cited rows · no vacuous zeros · LLM review
→
Answerverified claims only; causes the data can't prove are labelled "likely"

↺ Unsupported claims go back to the investigator with the critic's reasons (up to 2 repair rounds). Hard limits: 8-minute run deadline, step budget with forced finish, capped retries, single-SELECT guard.

Every role runs on NVIDIA Nemotron (nemotron-3-super-120b-a12b). The full trace is the World Model event log: question, hypotheses, each query and its rows, each critic verdict, the answer.

Trust

The critic decides what you get to read

Deterministic checks (no model)

  • Every claim cites evidence that was actually recorded.
  • Every year and 4+-digit number in a claim appears in the cited rows or SQL.
  • A zero result proves nothing if its filter value matches no rows (entity_name = 'Apple' when the table says "Apple Inc.").

Then an LLM review

  • Do the cited rows, and only those, show the claim? supported / partial / unsupported.
  • Rejected claims are sent back with reasons; the investigator gathers more evidence or drops them.
  • The final summary is written from verified claims only; a new number in it is rejected.

Caught during today's development runs: invented SIC codes (3599, 3500) not in any row, a "no rows" claim built on a misspelled company name, and partial claims sent back for proof.

Results

Honest limits · next

What is not done yet

  • Recorded samples and the eval use an offline mirror of the Zetaris views so they replay without keys; one run is live.
  • Asked which rows break the USL's DQ rules, the agent invents its own rules instead of reading SHOW DQ.
  • The critic is strict on numbers and citations, but can still accept a weak interpretation worded as a fact.
  • Small, bounded world: 3 companies, 2 revenue concepts.

Next

  • An agent-readable USL catalog + DQ endpoint (our Zetaris feature request), so the critic cites DQ results directly.
  • H-MEM "dreaming": propose general rules from many verified findings, with human approval.
  • A small web UI that shows each claim beside its rows.

Try it

Runs in minutes, no GPU, standard-library Python

# offline replay of the recorded runs, no keys needed
SAMPLE_MODE=true python -m explainwhy --sample 1

# live NVIDIA Nemotron on the local data mirror
python -m explainwhy "Why does Tesla report revenue under two different XBRL concepts?"

# live Nemotron + live Zetaris (falls back to the mirror, and says so, if unreachable)
python -m explainwhy --zetaris --sample 2

# offline tests with a scripted model
python -m pytest -q

Each run writes report.md (answer, verified and dropped claims, hypotheses, every query with its rows), result.json, events.jsonl (the trace) and trace.log. All code was written on 27 Oct 2026; no pre-existing components.
